# 写完就到草稿箱：<br>我把公众号这套流程拆开给你看

我写一篇公众号，花时间最多的地方，曾经不是写，是排版。

字号、行距、段间距、图片居中、引用块底色……每换一台设备、每换一个编辑器，格式就掉一次。一篇文章从写完到进草稿箱，排版能吃掉四十分钟。

现在这四十分钟是零。

不是因为我找到了什么神器，而是我把这件事拆成了两半：==需要人来判断的，我留着；不需要判断的，全部交出去。==

这篇不讲道理，只讲流程。你看完可以照着搭一套。

## 01 这套东西到底怎么跑

整条链路只有四步，前两步在网上，后两步在你电脑上。

第一步，AI 写一个 Markdown 文件。就是纯文本，没有任何格式花活。

第二步，一条命令把它渲成 HTML。页面里每个标签都自带样式，没有一行 `<style>`。

第三步，一条命令把 HTML 和图片一起送进公众号草稿箱。图片自动搬到微信的服务器上。

第四步，你打开后台，看一眼，点发表。

前三步可以一条命令跑完，也可以拆开跑。唯一不能自动的是第四步，原因我在第六节讲，那个限制本身就很有意思。

## 02 开工前，先备三样东西

**一个能在后台改配置的公众号。** 订阅号、服务号都行。你需要拿到两样东西：AppID 和 AppSecret，在「设置与开发 → 开发 → 基本配置」里。

**同一页下面的 IP 白名单。** 这一步最容易被忽略。微信只接受白名单里的 IP 调接口，你的电脑出口 IP 不在里面，所有请求都会返回 `40164`。家里宽带 IP 会变，变了就要重加。

**一台能跑 Python 的电脑。** 这一套全是脚本，不依赖任何第三方平台，你不需要买会员。

代码我放在一个仓库里，两个脚本加起来不到一千行：地址在文末。

## 03 第一步：让 AI 只写一个 Markdown

这一步的关键是==限制 AI 的输出形态==。

不要让它给你 HTML，不要让它调接口，就让它老老实实产出一个 `.md`。因为纯文本可以反复改，改完重跑一次命令就行，成本几乎为零。

文件顶部留一段元信息：

```markdown
---
title: 浏览器标签上的标题
label: 工具 · 实操
lead: 一句话导语
---
# 正文大标题
```

`label` 是标题上方的栏目标签，`lead` 是标题下方的灰色引子，都可以不写。

正文用一套极简语法，只有六种写法，学会不超过两分钟：

```markdown
## 01 小节标题
正文段落，==这句要高亮==。
> 引用或示例
![配图](img/a.jpg "图注")
1. 有序列表
:::card 卡片标题
1. 条目一
:::
```

意思是：小节标题以数字开头，自动生成序号块；`==` 包住的是高亮；`>` 是引用；`:::` 围起来的是卡片。

就这些。没有颜色、没有字号、没有对齐方式——**排版的所有决定权都在模板里，不在稿子里**。这是整套流程能稳定的根本原因：内容归内容，样式归样式，两边互不干扰。

## 04 第二步：一条命令，渲成微信能吃的 HTML

命令只有一行：

```bash
python3 wechat_layout.py article.md -o article.html
```

加 `--theme orange` 换个风格，加 `--fragment` 只输出正文片段（推送用这个）。

为什么非要转一次 HTML？因为这里有一个多数人不知道的坑：==微信编辑器会剥离 `<style>` 标签、外链字体和所有脚本。==

你从网页复制的样式，粘进去就散了，原因就在这。所以模板的做法是**全内联**——每个元素身上直接写 `style="..."`，不依赖任何外部文件。这样粘进编辑器，一个像素都不会掉。

渲完先在浏览器里看一眼。这一步就是你的校样，看到什么样，发出去就是什么样。

## 05 第三步：一条命令，送进草稿箱

```bash
python3 push_draft.py article.fragment.html \
    --cover cover.jpg \
    --title "文章标题" --digest "摘要"
```

它会自动做三件事，顺序不能反：

**搬封面。** 封面走「永久素材」接口，微信返回一个 `media_id`，填进草稿的封面字段。这个字段只认永久素材，随便给个图片链接是不行的。

**搬正文图。** 正文配图走另一个接口，返回的是 `mmbiz.qpic.cn` 开头的网址，脚本会把这些网址回填替换掉 HTML 里的本地路径。

**建草稿。** 一个请求带上标题、摘要、正文、封面，微信返回草稿 ID。这时候打开后台草稿箱，稿子已经在那儿了。

关于图片这一步，必须多说一句：**微信会把正文里的外链图片全部剥掉**。你贴一个图床链接进去，发出来就是一块空白。所以图片必须先上传，换成微信自己的域名——这也是为什么大部分「一键排版」工具，图片总是出问题。

## 06 最后一步，为什么必须你手动

我试过让它自动发表，接口返回 `48001`：接口未授权。

不是配置错了，是权限就没有。个人订阅号不在「发表」接口的开放范围内——草稿箱接口能用，群发接口和发表接口不给。

所以这套流程的天花板就是**草稿箱门口**。

我一开始觉得这是个遗憾，后来觉得挺好。发出去就收不回了，留一个人工确认的环节，反而安全。而且这个环节只花三十秒：扫一眼标题、扫一眼首图、点发表。

想真正做到「到点自动发」，只有服务号认证这一条路，那是另一个话题了。

## 07 改稿和踩过的坑

改稿不是删了重建。用草稿 ID 取回内容，改完覆盖同一篇，草稿箱里不会冒出一堆重复稿。这点很关键，我前面几版都是这么迭代的。

下面几个坑，都写进代码注释了，你照着做能省半天：

| 坑 | 现象 | 处理 |
|---|---|---|
| 中文被转义 | 正文显示成 `\u62d2\u7edd` | 序列化时关掉 ASCII 转义 |
| 标题太长 | 报 `45003` | 控制在 78 字节内 |
| 用 GET 取草稿 | 报 `43002` | 草稿接口全部用 POST |
| 更新时传了数组 | 报 `47001` | 传对象，不是数组 |
| IP 变了 | 报 `40164` | 回后台把新 IP 加进白名单 |

这几条没有一条是「技术难题」，全是文档里不显眼、但会让你卡一整晚的细节。

## 最后说一句

这套流程真正省下来的，不是那四十分钟排版时间。

是==心理成本==。以前想到「还要排版」就不想动笔，现在写完就是完事，剩下的事脚本干。写得多了，风格才慢慢稳下来。

工具不解决内容问题，但它能把「开始写」这件事的门槛压到最低。对我来说，这就够了。
